### 2.4 Supporting material excluded from the report

**Little's Law check** (N = throughput x mean latency, so W = N / rps), single worker:

| N | rps | W = N/rps (ms) | measured p50 (ms) |
|---|---|---|---|
| 1 | 179.5 | 5.6 | 5.5 |
| 4 | 195.0 | 20.5 | 20.3 |
| 8 | 200.2 | 40.0 | 38.3 |
| 16 | 201.5 | 79.4 | 77.8 |

Throughput is fixed near 200 rps, so W grows linearly with N: extra concurrency only queues. The no-queue
operating point is N ≈ rps x service time ≈ 200 x 0.0056 ≈ 1.1.

**Full 4-worker table** (`partA/loadtest_workers4.json`):

| Concurrency | Requests | rps | p50 ms | p95 ms | p99 ms | Errors |
|---|---|---|---|---|---|---|
| 1 | 780 | 195.0 | 4.6 | 7.3 | 9.0 | 0 |
| 2 | 1534 | 383.5 | 5.0 | 6.1 | 7.3 | 0 |
| 4 | 1489 | 372.2 | 10.9 | 19.2 | 23.8 | 0 |
| 8 | 2293 | 573.2 | 13.0 | 24.0 | 32.5 | 0 |
| 16 | 2398 | 599.5 | 24.0 | 52.5 | 68.9 | 0 |
| 32 | 2421 | 605.2 | 45.1 | 111.1 | 149.5 | 0 |

Notes: capacity under the SLO went from 200.2 rps (concurrency 8) to 599.5 rps (concurrency 16), about 3.0x
(peak 2.8x). The dip at concurrency 4 (372 rps, no better than concurrency 2) is unexplained; a possible cause is
uneven keep-alive connection distribution across workers (hypothesis, not verified). With several workers the
`/metrics` counters are per process.

**Batch runs:** batch 1 gave 170.2 rps, p50 5.9 ms (5.88 ms/row); batch 100 gave 183.0 rps, p50 6.0 ms
(0.0546 ms/row, about 108x cheaper per row, 18,300 rows/s). The batch-1 rate differs about 5% from the
concurrency-1 row of the main table: run-to-run noise. The marginal per-row cost is too small to measure at this
resolution.

**Limitations:** each level ran once for 4 s; the load generator and server share one machine; the generator is
closed-loop, so numbers describe sustained throughput, not behaviour under a fixed arrival rate.

**Design notes for `eta_app.py`:** model loaded once at import into the module-level `model`; a single middleware
handles request IDs, metrics and the generic 500; metrics are hand-rolled (no `prometheus_client`), per process;
the infeasible rule is a pydantic `model_validator` (422 with "infeasible" in the message).

## 3. Part B — MLflow registry, gate, shadow

Always set the tracking URI first (SQLite store, created in the current folder):

```bash
export MLFLOW_TRACKING_URI=sqlite:///mlflow.db
```

Run `register` as a script (not via `import`), so the pyfunc class is pickled by value and `mlflow models serve`
does not need `eta_mlflow.py` on its path. Running `register` again creates new versions (3, 4, ...); to start
clean, delete `mlflow.db` and `mlruns/` first.

| Required result | Command |
|---|---|
| B1: register both models, aliases prod->v1, candidate->v2 | `python partB/eta_mlflow.py register` |
| B1: registry table (version, bundle, alias) | `python partB/eta_mlflow.py table` |
| B2: unit tests of `decide()` | `python -m pytest partB -q` |
| B2: gate, default thresholds | `python partB/eta_mlflow.py gate \| tee partB/gate_output.txt` |
| B2: gate, `min_rel_gain=0.60` | `python partB/eta_mlflow.py gate --min-rel-gain 0.60 \| tee -a partB/gate_output.txt` |
| B3: shadow comparison | see below |

### 3.1 Shadow comparison (three terminals)

```bash
# terminal 1
mlflow models serve -m "models:/eta-model@prod"      -p 5101 --env-manager local
# terminal 2
mlflow models serve -m "models:/eta-model@candidate" -p 5102 --env-manager local
# terminal 3, after both servers report they are listening
python partB/shadow_compare.py | tee partB/shadow_output.txt
```

If your MLflow rejects `--env-manager local`, check `mlflow models serve --help` for the current flag. Stop both
servers (Ctrl+C) when done. `shadow_compare.py` sends the same 200 single-row requests from `data/eta_fresh.csv`
to both ports (after one warm-up call each, not counted) and reports (i) mean absolute difference, (ii) percentage
differing by more than 10 minutes, (iii) p95 latency per server.

### 3.2 Results and notes excluded from the report

Gate metrics (fresh data `make_data(2000, seed=99)`, p95 over 200 single-row in-process predictions):

| | prod (v1) | candidate (v2) |
|---|---|---|
| MAE (min) | 11.955 | 6.105 |
| MAE rush (min) | 19.68 | 8.58 |
| MAE rain (min) | 11.623 | 6.285 |
| p95 (ms) | 1.20 | 1.11 |

Relative MAE gain 48.9%. Default thresholds: all four criteria true, `promote: true`. With
`min_rel_gain=0.60`: only `overall_gain` is false, `promote: false`.

Shadow results: mean |diff| 9.48 min; 35.0% of requests differ by more than 10 min; p95 11.7 ms (prod) and
11.4 ms (candidate); mean prediction 118.93 (prod) / 119.02 (candidate) min.

- **Slice rule:** interpreted as relative: candidate slice MAE <= prod slice MAE x (1 + `max_slice_regression`).
- **Criteria keys returned by `decide()`:** `overall_gain`, `latency`, `rush_slice`, `rain_slice`; `promote` is their conjunction.
- **Tests (9):** clear win; gain boundary (just inside, exactly on, just outside, using exact-arithmetic thresholds
  such as `min_rel_gain=0.25`); no/negative improvement; latency boundary; rush-slice and rain-slice regression
  blocking a promotion despite a big overall gain; small regression within tolerance; strict `min_rel_gain=0.60`;
  purity (inputs not mutated).
- **In-process vs HTTP latency:** the gate's ~1.1 ms p95 is the model call through the pyfunc; the ~11 ms shadow
  p95 also includes HTTP handling, JSON parsing and MLflow schema enforcement.
- **Harmless warnings:** MLflow warns about missing type hints on `predict` and about CloudPickle serialization of
  a Python-object model.
- **Signature:** all inputs are declared `double`, so integer JSON values are accepted.

## 4. Part C — Ray Serve sticky canary

Needs Ray Serve installed (it is in `requirements.txt`; it worked on Python 3.14.6 here). Ray's cluster is started
with `num_cpus=2` by the script. `verify_ray.py` uses port **8100** by default so it does not collide with the Part A
server on 8000; override with `SERVE_PORT=<port>`.

| Required result | Command |
|---|---|
| C1: build the app | `import eta_ray; eta_ray.build(weight=0.1, extra_work_ms=0.0)` (used by the script below) |
| C2: all five checks, written to `partC/verify_output.txt` | `python partC/verify_ray.py` |

Before a (re)run: `ray stop --force` (clears leftovers from an interrupted run). Expect about a minute of startup.
A successful run ends with `ALL CHECKS PASSED`; the output file is written even if a check fails.

### 4.1 Results and notes excluded from the report

```
(a) share routed to candidate at weight 0.2: 0.182 (target 0.2 +/- 0.04)
(b) 200 customers, second call: 0 changed arm
(c) after delete + redeploy of identical app: 0 of 200 changed arm
(e) X-Beta: 1 on 50 prod-arm customers: 50/50 routed to v2
(d) weight 0.2 -> 0.5: share now 0.496; 0 of 182 former candidate customers moved back to prod
ALL CHECKS PASSED
```

- The script runs (e) before (d), so the output order is a, b, c, e, d.
- 0.182 is about 1.4 standard errors below 0.2 (sd = sqrt(0.2*0.8/1000) ≈ 0.013): sampling noise, not a hash bias.
- **Design:** deployments `EtaModel` (used for prod, 2 replicas, and the candidate, autoscaling 1-3) and a FastAPI
  `Router`. Arm = `v2` if `X-Beta: 1` or `bucket(customer_id) < weight`, where bucket = first 8 bytes of
  SHA-256(`salt:customer_id`) / 2^64. The salt is fixed (`eta-canary-v1`); changing it re-randomises everyone.
- **CPU budget:** router 0.25 + prod 2 x 0.25 + candidate 1 x 0.25 = 1.0 in use (Ray reported 1.0 of 2 free);
  at the autoscaling maximum 0.25 + 0.5 + 3 x 0.25 = 1.5 CPUs (arithmetic, not tested).
- **Autoscaling config:** `min_replicas=1, max_replicas=3, target_ongoing_requests=2, upscale_delay_s=5,
  downscale_delay_s=60`. Scale-up/scale-down under load was not exercised.
- `extra_work_ms` (busy-wait inside the model call) exists to simulate a heavier model for autoscaling experiments.

## 5. Part D — Release gate (smoke test)

`partD/smoke_eta.py --url ... --expect-version ...` prints PASS/FAIL per check and exits 0 (all pass) or 1.
Optional flags: `--max-p95-ms` (default 80), `--format rest|mlflow` (default rest), `--header "X-Beta: 1"`.

Check the file parses, then run with the Part A server up (terminal 1, port 8000):

```bash
python -m py_compile partD/smoke_eta.py && echo syntax ok

# pass case
python partD/smoke_eta.py --url http://localhost:8000/v1/models/eta:predict --expect-version v1
echo "exit code: $?"          # run without a pipe, otherwise $? is tee's exit code

# deliberate failure (v1 server, wrong expected version) -> expect a FAIL line and exit code 1
python partD/smoke_eta.py --url http://localhost:8000/v1/models/eta:predict --expect-version v2
echo "exit code: $?"
```

Other targets:

```bash
# Part B MLflow server (start it as in 3.1)
python partD/smoke_eta.py --url http://localhost:5101/invocations --format mlflow --expect-version v1
python partD/smoke_eta.py --url http://localhost:5102/invocations --format mlflow --expect-version v2
# Part A server restarted on v2: ETA_MODEL=../data/eta_v2.joblib uvicorn eta_app:app --port 8000
python partD/smoke_eta.py --url http://localhost:8000/v1/models/eta:predict --expect-version v2
# Part C (the router returns the arm's version; force the candidate with the header)
python partD/smoke_eta.py --url http://127.0.0.1:8100/v1/models/eta:predict --header "X-Beta: 1" --expect-version v2
```

(The Part C command needs a Ray Serve app running on port 8100, e.g. start it from a Python session with
`serve.start(http_options={"port": 8100}); serve.run(eta_ray.build(weight=0.2), route_prefix="/")`. Not tested here.)
